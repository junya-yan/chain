# CHAIN

**A physics-based chain-reaction puzzle game for the browser.**

**▶ Play: https://junya-yan.github.io/chain/**

*Read this in other languages: [日本語](README.ja.md)*

---

Animals walk on their own. The player never controls them directly — you only
place items beforehand to build a path, then watch the simulation play out.

Inspired by *Puzzling*, part of the Daiso "The Game Series". This is a personal
study project published on GitHub and is not intended for commercial use.
See [Rights and Credits](#rights-and-credits) for details.

## Getting Started

Requires Node.js 20 or later.

```bash
npm install
npm run dev
```

| Script | Description |
| --- | --- |
| `npm run dev` | Start the Vite development server |
| `npm run build` | Type-check and produce a production build |
| `npm run preview` | Serve the production build locally |
| `npm run typecheck` | Type-check only |
| `npm run verify` | Verify every stage headlessly (see below) |

## Verifying Stages

Physics puzzles invite the assumption that a stage "must be solvable". Each
stage JSON carries an intended solution (`solution`), and the following command
replays it in a headless simulation to confirm that it really is:

```bash
npm run verify
```

Five checks run for every stage:

1. Whether the intended solution is **placeable under the placement rules** —
   this catches stages that work physically but cannot actually be set up in the UI.
2. Whether the intended solution really clears the stage.
3. Whether the stage **fails when nothing is placed** — this catches stages
   where placing items is pointless.
4. Whether the intended solution uses no more items than `par`.
5. Whether running the same placement twice produces identical results
   (a regression test for determinism).

For check 1, placement validity lives in `src/sim/placement.ts` rather than in
the UI. Keeping it only in the UI would leave a hole that verification could
not see through.

## Architecture

| Directory | Role |
| --- | --- |
| `src/sim/` | Physics and game rules. **No DOM dependencies whatsoever** |
| `src/render/` | Canvas rendering |
| `src/ui/` | Screens and input |
| `public/stages/` | Stage definitions (JSON) |
| `public/sprites/` | Character images (optional; falls back to procedural drawing) |
| `tools/` | Verification scripts |

Because `src/sim/` is independent of the DOM, it produces the same results in
the browser and in Node. `npm run verify` relies on this.

### Determinism

To guarantee that the same placement always yields the same outcome, the
simulation:

- Uses no randomness at all. Background decoration uses a fixed-seed
  pseudo-random generator, and that is purely cosmetic.
- Always iterates in array order. Contact generation order follows body array
  order as well.
- Avoids `Math.hypot` in hot loops, since its precision is implementation
  dependent. `Math.sqrt` is exact under IEEE 754.

### Physics

A hand-written 2D rigid-body solver using sequential impulses (translation and
rotation). Separating axes are found with SAT, contact points are generated by
clipping the incident face against the reference face, and accumulated impulses
are warm-started across frames.

Walking animals propel themselves through a **target tangential velocity in the
friction solver**, not by directly assigning velocity. Direct assignment would
be treated as sliding by the friction solver on the next step and cancelled out.
With this approach, legs grip the ground on slopes and slide back down naturally
when a slope is too steep.

## Adding a Stage

Drop a JSON file into `public/stages/` and add its id to `index.json`. No code
changes are needed. `src/sim/types.ts` is the single source of truth for the
schema, and the loader validates against it at load time.

```json
{
  "id": "amazon-04",
  "name": "Stage name",
  "biome": "amazon",
  "brief": "Objective shown at the start",
  "mission": { "type": "reach_goal", "target": "tiger" },
  "protect": ["tiger"],
  "world": { "gravity": 1400, "bounds": { "w": 800, "h": 600 }, "timeLimit": 60 },
  "terrain": [{ "material": "rock", "x": 400, "y": 480, "hw": 420, "hh": 90 }],
  "actors": [{ "type": "tiger", "x": 700, "y": 375, "dir": -1 }],
  "props": [{ "type": "goal", "id": "crown", "x": 70, "y": 272, "hw": 24, "hh": 28 }],
  "inventory": [{ "item": "rope", "count": 1 }],
  "par": 1,
  "hints": ["Hints revealed progressively"],
  "solution": [{ "id": "p0", "item": "rope", "x": 0, "y": 0,
                 "from": { "target": "anchorA" }, "to": { "target": "anchorB" } }]
}
```

The origin is the top-left corner and y points downward. Always write a
`solution` — without it, verification cannot run.

### Numbers That Shape Stage Design

Walking animals cannot jump, so terrain is tightly constrained by these values.

| Behaviour | Value | Meaning |
| --- | --- | --- |
| Walking speed | 62 px/s | |
| Climbable step | 13 px | Anything higher counts as a wall and the animal turns back |
| Rope climbing | 52 px/s | The only means of vertical movement |
| Jump-off from the top of a rope | vx 95 / vy 70 | Sets the maximum reach to a neighbouring platform |

A `platform` is 72 px wide. **A gap wider than that cannot be bridged with a
single platform** — if both ends do not rest on terrain, it falls. Provide a
rope wherever terrain requires vertical movement.

A `bridge` is placed by picking two points, the same way a rope is. **Its sag
is about 0.18x the distance between those two points** and barely changes
under load, because the planks do not stretch. The deck only hinges every
60 px: any finer and the plank underfoot is lighter than the animal and moves
too much for it to push off, so it never gets across (the finer planks you see
are drawn, not simulated). Measured maximum usable span is around 300 px.

A balloon rises only until its rope is fully taut, so the rope length — the
distance between the two points at placement time — determines the balloon's
final height.

## Character Art

Rendering has three tiers, and the first one available is used.

1. **Rig** (`public/sprites/rig.json`) — a single illustration split into parts
   and animated by rotating joints
2. **Sprite sheet** (`public/sprites/manifest.json`) — frame-by-frame images
3. **Procedural drawing** — the game is fully playable with no images at all

**Do not use GIFs.** Walk frames are synchronised to the actual distance
travelled, and the game supports 2x/4x fast-forward and pausing. A GIF runs on
its own clock, so the art would drift out of sync with the physics. Its
transparency is also 1-bit, which leaves ragged outlines against dark
backgrounds. See [docs/sprites.md](docs/sprites.md) for details, and
[docs/ai-prompt.md](docs/ai-prompt.md) for the prompts used with image
generation models.

### Turning AI-Generated "Sheet-Like" Art into a Usable Sheet

Image generation models cannot keep frames consistent and tend to produce
"posters" with backgrounds, frames, and labels baked in.
`tools/extract-frames.py` recovers a usable sheet from those.

```bash
python3 tools/extract-frames.py art-source/tiger.png public/sprites/tiger.png
```

- Flood-fills inward from the border to strip the baked-in background
  (the character's dark outline acts as a dam)
- Targets the ground the feet stand on using colour samples taken from the
  bottom edge of each cell
- Keeps only the largest connected component, dropping debris such as rocks
- **Normalises height and foot level across every frame** — generative models
  never get this right, and without it the walk cycle judders

`public/sprites/tiger.png` is currently produced by this process (11 frames).
Thresholds need tuning per illustration. Measured upper bounds for the tiger art:

| Constant | Value | What happens above it |
| --- | --- | --- |
| `TOLERANCE` | 34 | At 40 or above, the fill breaks through the outline and splits the body |
| `GROUND_MATCH` | 10 | At 14 or above, the shoes start to erode |

## Items

| Item | Behaviour |
| --- | --- |
| Platform | Serves as footing or a ramp. Tilt it and objects slide |
| Bridge | Strung between two points. Sags under its own weight. Animals walk across it |
| Balloon | Floats upward and lifts whatever it is tied to. Pops on spikes or blasts |
| Rope | Connects two points and can be climbed. Burns from one end when lit, and eventually snaps |
| Bomb | Explodes shortly after being lit. Startles birds into flight and blows objects away |
| Spring | Launches whatever touches it |
| Weight | Very heavy. Falls and crushes objects |
| Pulley | Carries a rope and redirects force |

## Known Issues

- `tiger.png` has only a few frames, and a thin line of ground cracking remains
  near the tail. The proper fix is a single standing illustration converted to
  the rig approach (format documented in the rig.json section of
  [docs/sprites.md](docs/sprites.md)).
- Frames in the source sheet drift in posture, so the walk cycle does not loop
  cleanly.
